# Развёртывание центра

## Служебная зона

Схеме нужен домен, которым вы управляете, — под ним живёт acme-dns.
С доменами, которые вы закрываете сертификатами, он не связан.

Достаточно зоны третьего уровня под доменом, который у вас уже есть:
отдавать целый домен на обслуживание не нужно. `example.com` в примерах —
плейсхолдер из RFC 2606.

Служебная зона нужна постоянно, а не только на время запуска: на выданные
в ней имена ссылаются CNAME всех ваших доменов. Если зона перестанет
обслуживаться, прекратятся все продления.

## Однократная настройка DNS

Две записи в зоне вашего домена у регистратора — больше в ней ничего не
меняется:

    ns-acme.example.com.  A   <публичный IP этого хоста>
    acme.example.com.     NS  ns-acme.example.com.

Порт 53 должен быть доступен из интернета по UDP и по TCP: сюда приходит
Let's Encrypt.

Если на хосте работает `systemd-resolved` — а на Ubuntu он работает по
умолчанию, — 53-й порт уже занят его stub-listener'ом на `127.0.0.53`.
Привязка ко всем адресам с этим конфликтует, поэтому укажите в
`ACMEDNS_BIND_IP` публичный адрес хоста: адреса разные, конфликта нет,
и хостовый DNS трогать не придётся.

    sudo ss -lunp 'sport = :53'    # кто держит порт

## Запуск

Файла конфигурации у центра нет — всё задаётся переменными окружения,
конфиг acme-dns генерируется из шаблона при старте:

    cp .env.example .env
    # заполните ACMEDNS_*, ACME_EMAIL и пароль администратора
    echo "LEAUTH_MASTER_KEY=$(openssl rand -hex 32)" >> .env
    echo "LEAUTH_ENROLL_TOKEN=$(openssl rand -hex 32)" >> .env
    # мастер-ключ положите ещё и в хранилище секретов

    docker compose up -d

| Переменная | Значение |
|---|---|
| `ACMEDNS_ZONE` | делегированная зона, `acme.example.com` |
| `ACMEDNS_NS_HOST` | имя NS-сервера из делегации, `ns-acme.example.com` |
| `ACMEDNS_ADMIN` | почта админа зоны в форме SOA, см. ниже |
| `ACMEDNS_PUBLIC_IP` | публичный IP этого хоста |
| `ACMEDNS_BIND_IP` | адрес, на котором слушать 53-й порт; по умолчанию все |
| `LEAUTH_MASTER_KEY` | 64 hex-символа, шифрует приватные ключи в БД |
| `LEAUTH_ENROLL_TOKEN` | общий токен приёма прокси |
| `ACME_EMAIL` | почта для уведомлений Let's Encrypt |
| `ADMIN_PASSWORD` | пароль к странице статуса |
| `LEAUTH_BIND_IP` | адрес публикации API; по умолчанию все, см. ниже |

Незаданная переменная останавливает запуск: acme-dns с пустой зоной
стартует молча и не отвечает ни на один запрос.

Всё, что перечислено ниже, задаётся в том же `.env`: он целиком уезжает
в контейнер центра, поэтому дописывать переменные в `docker-compose.yml`
не нужно.

Необязательные: `ACME_DIRECTORY` (по умолчанию боевой Let's Encrypt),
`ADMIN_USER` (`admin`), `LEAUTH_LISTEN` (`:8080`), `LEAUTH_DB`
(`/data/leauth.db`), `ACMEDNS_API`, `RENEW_BEFORE` (`720h`),
`CHECK_INTERVAL` (`5m`).

`PRECHECK_RESOLVER` — список рекурсивных резолверов через запятую, по
умолчанию `1.1.1.1:53,8.8.8.8:53`. Через них центр проверяет, что CNAME
домена указывает на выданное имя, и через них же lego разрешает CNAME
перед заказом. Порт можно не писать; адрес IPv6 пишется в скобках —
`[2001:4860:4860::8888]:53`.

Резолверы опрашиваются по кругу, пока проба не найдётся: недоступность
одного из них выпуск не останавливает. Поэтому их и стоит указывать
несколько — список из одного адреса делает его единственной точкой отказа.

`PROPAGATION_TIMEOUT` (`5m`) — верхняя граница ожидания в lego. Записи
acme-dns появляются мгновенно, так что этот запас нужен только на
случай задержек на стороне ACME.

### Почему проверка распространения не включена

У lego есть две встроенные проверки, и обе центру не подходят.
Авторитативная резолвит имя NS-сервера acme-dns, из-за чего выпуск
начинает зависеть от того, видно ли это имя из контейнера.

Проверка через рекурсивные резолверы отправляет запросы с
`RecursionDesired=0`. Публичный резолвер на такой запрос отвечает
только из кеша, а TTL записей acme-dns равен секунде — кеш почти всегда
пуст, и возвращается SERVFAIL. Выпуск превращается в лотерею: пройдёт
он или нет, зависит от того, успела ли проверка в ту же секунду, что и
предыдущий запрос с рекурсией.

Проверяет владение доменом сам Let's Encrypt, обращаясь к вашему
acme-dns напрямую. Со стороны центра достаточно precheck: он обычным
рекурсивным запросом убеждается, что CNAME на месте, и не пускает
домен в ACME, пока записи нет.

Проверка идёт в два шага. Сначала дешёвый запрос CNAME: если записи в
зоне нет или она указывает не на выданное имя — домен ждёт человека, и
дальше идти незачем. Только когда CNAME на месте, центр пишет в acme-dns
случайное пробное значение и убеждается, что видит его через резолвер, —
так проверяется весь путь целиком, а не только первое звено.

Первый шаг нужен ради доменов, которые ждут CNAME сутками: без него
каждый из них тратил бы запись в acme-dns на каждом тике планировщика.
Молчащий резолвер отсутствием записи не считается — в этом случае
проверка идёт дальше пробой.

## Обслуживание

| Команда | Что делает |
|---|---|
| `docker compose exec leauth leauth revoke <имя-прокси>` | отзывает токен прокси и снимает с него домены |
| `docker compose exec leauth leauth renew <домен>` | помечает домен на перевыпуск при ближайшем тике |

Обе работают с базой напрямую и не требуют остановки центра.

## Приём прокси

Токенов вручную выдавать не нужно. Новый прокси приходит с общим
`LEAUTH_ENROLL_TOKEN`, называет своё имя и получает персональный токен,
который сохраняет у себя в томе. В базе центра лежит только хеш.

Когда парк собран, приём закрывается: уберите `LEAUTH_ENROLL_TOKEN`
из `.env` и перезапустите центр. Уже принятые прокси продолжат работать,
новые получат отказ.

Прокси, потерявший свой том, придёт повторно под тем же именем и получит
новый токен; домены за ним сохранятся. Для этого `LEAUTH_ENROLL_TOKEN`
удобнее оставить заданным.

### Что даёт персональный токен

Токен именует прокси — но не ограничивает его набором доменов. Прокси
объявляет центру, какие сертификаты ему нужны, и центр отдаёт их: домен,
заявленный впервые, заводится, уже существующий — выдаётся вместе с
приватным ключом. Так работают переезд и балансировка, когда один домен
обслуживают несколько прокси.

Отсюда следует ровно одно, и знать это нужно заранее:

> **Любой принятый прокси может запросить любой домен установки и получить
> его приватный ключ.** Токены разграничивают, *кто* пришёл, а не *что* ему
> доступно.

В логе центра такое видно — заявку на чужой домен он отмечает
предупреждением:

    домен заявлен ещё одним прокси домен=bank.example.com прокси=srv-07
    уже обслуживают=[srv-01]

Практический вывод: прокси в этой схеме равны по доверию. Если один из
них заметно менее доверенный, чем остальные, — ставьте ему отдельный
центр, а не отдельный токен.

### Отзыв прокси

Скомпрометированный прокси отключается на центре:

    docker compose exec leauth leauth revoke srv-07

Токен перестаёт действовать сразу, домены снимаются с обслуживания. Сами
домены и их учётки acme-dns остаются: другой прокси подхватит их без
нового CNAME.

Если общий токен приёма скомпрометирован вместе с прокси, отзыва мало —
по нему прокси представится заново под тем же именем и получит свежий
токен. Тогда сначала смените `LEAUTH_ENROLL_TOKEN` в `.env` центра и
перезапустите его, а потом отзывайте. Остальные прокси этого не заметят:
свои токены у них уже есть, а `enroll_token` нужен только при первом
запуске.

Домены, которые обслуживал отозванный прокси, после этого нужно
перевыпустить: их приватные ключи он унёс с собой и действуют они до
конца срока сертификата. Отзыв сам по себе этого не делает:

    docker compose exec leauth leauth renew bank.example.com

Домен снимается со статуса `active`, и планировщик выпускает его заново
на ближайшем тике — как новый, но без участия человека: CNAME уже на
месте. Уцелевшие прокси заберут свежий сертификат при следующей
синхронизации. Старый при этом не отзывается в Let's Encrypt; если ключ
точно скомпрометирован, отзовите сертификат у CA отдельно.

## acme-dns без docker-proxy

Опубликованный порт `53/udp` обслуживает процесс `docker-proxy`: он
принимает пакеты на хосте и пересылает их в контейнер. Для UDP это
лишнее звено — оно держит по сокету на каждый адрес источника и при
плотном потоке запросов от рекурсивных резолверов может терять пакеты.
Потери происходят в пользовательском пространстве, поэтому в счётчиках
`netstat -su` их не видно.

Убрать посредника, не меняя настроек Docker, можно отдав acme-dns сеть
хоста. В `deploy/central/docker-compose.override.yml`:

```yaml
services:
  acme-dns:
    network_mode: host
    ports: !reset []
```

и в `.env`:

    ACMEDNS_LISTEN=203.0.113.10:53

Адрес обязателен: в сети хоста `0.0.0.0:53` столкнётся с stub-listener
systemd-resolved на `127.0.0.53`. `ACMEDNS_BIND_IP` при этом не нужен —
публикации портов больше нет.

## API центра под TLS

По умолчанию центр слушает открытый HTTP. По этому каналу ходят
персональные токены прокси и приватные ключи сертификатов, поэтому в
интернет его выставлять не следует.

Собственный сертификат центру взять неоткуда — он и есть тот, кто их
выпускает. Поэтому центр закрывается прокси на том же хосте: прокси
получает сертификат обычным путём, а до API ходит по localhost.

Эндпоинт в `agent.yaml` этого прокси:

```yaml
  - domain: leauth.example.com
    listen: 443
    upstream: http://127.0.0.1:8080
```

Страница статуса и без того закрыта паролем администратора — под TLS он
перестаёт ходить открытым текстом.

Если хочется закрыть её ещё и GitLab, выведите из-под авторизации путь
API: за токенами и сертификатами сюда ходят прокси, а не люди, и
браузерный вход их остановит.

```yaml
  - domain: leauth.example.com
    listen: 443
    upstream: http://127.0.0.1:8080
    upstream_auth:
      user: admin
      password: ${ADMIN_PASSWORD}
    oauth:
      groups: [platform/sre]
      skip_paths: [/api/]
```

`upstream_auth` избавляет от второго входа: пароль администратора
подставляет сам прокси, человек вводит только GitLab. На `/api/` это не
влияет — прокси приходят со своим `Bearer`, а подстановка срабатывает
только при пустом заголовке.

Адрес `127.0.0.1:8080` доступен прокси, только если тот работает в сети
хоста (`network_mode: host`). Прокси в обычной сети compose до localhost
хоста не достучится — подключите его к сети центра и ходите по имени
сервиса:

```yaml
    upstream: http://leauth:8080
```

### Порядок переключения

Последовательность важна: закрыв порт раньше времени, вы отрежете прокси
от центра, и они не смогут ни продлить сертификаты, ни узнать новые.

1. Заведите домен центра на прокси и дождитесь сертификата: A-запись,
   CNAME `_acme-challenge`, статус `active` на странице центра.
2. Проверьте, что API отвечает по HTTPS:
   `curl -si https://leauth.example.com/ | head -1` — ожидается 401,
   страница статуса под паролем.
3. Переключите остальные прокси: `server: https://leauth.example.com`
   в `agent.yaml`, затем `docker compose up -d`. Персональные токены
   при смене адреса сохраняются — они лежат в томе прокси.
4. Убедитесь, что все прокси синхронизировались: на странице центра у
   доменов обновилось время последней проверки.
5. Закройте порт: `LEAUTH_BIND_IP=127.0.0.1` в `.env` центра и
   `docker compose up -d`.

Прокси на том же хосте, который обслуживает домен центра, продолжает
ходить на `http://127.0.0.1:8080` — этот трафик хост не покидает.

Цена решения: удалённые прокси зависят от этого прокси. Пока он лежит,
они не синхронизируются — но выпуск и продление идут в центре и от
прокси не зависят, так что сертификаты не протухнут.

### Формат ACMEDNS_ADMIN

В SOA-записи почта пишется без `@`: собака заменяется точкой, а точки
внутри имени ящика экранируются обратным слешем.

| Почта | Значение переменной |
|---|---|
| `hostmaster@example.com` | `hostmaster.example.com` |
| `a.ivanov@example.com` | `a\.ivanov.example.com` |

Поле информационное: Let's Encrypt его не читает, на выпуск сертификатов
оно не влияет. Проще взять адрес без точек в имени ящика — по RFC 2142
для этого и существует `hostmaster@`.

Проверка после запуска:

    dig @<IP> acme.example.com SOA

Ответ должен содержать `ACMEDNS_NS_HOST` и `ACMEDNS_ADMIN`.

Правка `.env` и `docker compose up -d` перегенерируют конфиг. Но менять
`ACMEDNS_ZONE` после того, как выпущен хотя бы один сертификат, нельзя:
имена, выданные доменам, содержат старую зону, и все прописанные CNAME
станут указывать в никуда. Смена зоны означает переписать CNAME у всех
доменов.

## Сборка образов для серверов

Сборочная машина обычно arm64, серверы — amd64, поэтому образы собираются
кросс-платформенно. Бинарь собирается с `CGO_ENABLED=0`, так что никакой
эмуляции при сборке не нужно.

    make images                       # локально, под linux/amd64
    make push REGISTRY=ghcr.io/ваша-организация

Публиковать образы в реестр — включая публичный — безопасно: внутри только
статический бинарь и системные CA-сертификаты. Конфигурация, мастер-ключ,
токены и база монтируются на запуске и в слои образа не попадают.

Секреты живут вне образов и вне git:

- `deploy/central/.env` и `deploy/proxy/agent.yaml` — в `.gitignore`;
- `LEAUTH_MASTER_KEY` и токен приёма — в вашем хранилище секретов;
- тома `leauth-data` и `acme-dns-data` — в бэкапе.

## Что нельзя терять

Тома `leauth-data` и `acme-dns-data`. В них лежат учётные данные acme-dns:
при их потере все выданные CNAME станут недействительными, и каждому
домену придётся прописывать CNAME заново. Настройте бэкап обоих томов.

Мастер-ключ хранится отдельно от БД. Без него приватные ключи
сертификатов в БД не расшифровать.
