# Развёртывание прокси

    cp agent.yaml.example agent.yaml   # домены, порты, upstream
    cp .env.example .env               # токен приёма, реквизиты GitLab
    docker compose up -d

Прокси сам представляется центру и получает персональный токен, который
хранит в томе с сертификатами. На центре при этом делать ничего не нужно.

При первом запуске в логе появится предупреждение вида:

    нужен CNAME домен=foo.example.com запись=_acme-challenge.foo.example.com
    значение=<uuid>.acme.example.com

Пропишите эту запись в зоне домена — один раз и навсегда. Продление
сертификата ничего в зоне менять не будет. До появления записи прокси
работает на самоподписанном сертификате, то есть отвечает, но браузер
показывает предупреждение.

Пока хотя бы один домен работает на заглушке, прокси опрашивает центр
раз в минуту, а не по `poll_interval`. Как только все сертификаты
выпущены, он возвращается к обычному интервалу — обе смены режима видны
в логе.

Тот же список доменов со статусами виден на странице центра — там же
видно, какой прокси какие домены обслуживает.

## Один CNAME на зону

По умолчанию сертификат заказывается на каждый домен, и CNAME тоже нужен
на каждый. Если поддомены живут в одной зоне, объявите её:

    wildcard_zones:
      - example.com

Тогда на `example.com` и `*.example.com` выпускается один сертификат,
все эндпоинты внутри зоны используют его, а CNAME прописывается один раз.
Wildcard покрывает ровно один уровень: `docs.example.com` под него
подпадает, `a.docs.example.com` — нет.

## Изменение списка доменов

Список эндпоинтов в `agent.yaml` — это желаемое состояние целиком.
Прокси объявляет его центру при каждой синхронизации: добавленный домен
заводится, удалённый снимается с обслуживания и перестаёт продлеваться.
Запись домена и его учётка acme-dns при этом сохраняются, поэтому
вернуть домен можно без нового CNAME.

## Порты и апстримы

Домены на одном порту различаются по SNI, поэтому `listen` у всех
эндпоинтов может быть одинаковым:

    endpoints:
      - domain: docs.example.com
        listen: 8443
        upstream: http://docs:8080
      - domain: metrics.example.com
        listen: 8443
        upstream: http://metrics:9090

Так публикуется один порт, а адреса эндпоинтов отличаются только именем
домена — включая redirect URI в GitLab. Разные порты тоже допустимы,
если так удобнее разграничивать доступ файрволом.

Порт из `listen` должен быть опубликован. Первый задаётся переменной
`PROXY_PORT` (по умолчанию 8443), остальные добавляются в
`docker-compose.override.yml` — compose читает его автоматически, а git
не видит:

    cp docker-compose.override.yml.example docker-compose.override.yml

Это единственное место, где `agent.yaml` и `docker-compose.yml` обязаны
совпадать вручную, и разъезжаются они молча: прокси поднимется и будет
работать, но снаружи на неопубликованный порт никто не достучится.
Поэтому агент при старте печатает список:

    nginx займёт порты — они должны быть опубликованы наружу порты=[8443 9443]

Сверьте его с `ports` в compose после каждой правки `listen`.

Апстрим адресуется именем сервиса в сети compose и резолвится на каждом
запросе, поэтому прокси поднимается и перезагружается независимо от того,
жив ли бэкенд.

Путь в `upstream` не поддерживается: запрос уходит на бэкенд как есть,
поэтому `http://app:3000/prefix` молча потерял бы префикс — агент такой
конфиг не принимает. Домены и адреса бэкендов проверяются на форму:
всё, что попадает в конфиг nginx, обязано быть именем, а не выражением.

### Бэкенд со своей авторизацией

Приложение, закрытое basic-авторизацией, не нужно открывать ради прокси.
Реквизиты подставляет сам прокси:

```yaml
  - domain: prom.example.com
    listen: 8443
    upstream: http://metrics:9090
    upstream_auth:
      user: admin
      password: ${PROM_PASSWORD}
    oauth:
      groups: [platform/sre]
```

Пользователь входит через GitLab и пароля приложения не видит. Пароль
берётся из окружения — в `agent.yaml` его писать не обязательно.

Подстановка срабатывает, только когда клиент не прислал своего заголовка
`Authorization`. Машинные клиенты со своими токенами продолжают работать,
в том числе на путях из `skip_paths`.

Готовая строка `Basic …` попадает в конфиг nginx внутри контейнера,
поэтому файл создаётся с правами `0600`. Пароль виден тому, кто получил
доступ к контейнеру, — как и любой секрет из окружения.

### Бэкенд в чужой сети

Приложение, поднятое другим compose-проектом или ansible, стоит в своей
docker-сети. Публиковать его порт на хост ради прокси не нужно —
подключите прокси к этой сети в `docker-compose.override.yml`:

```yaml
services:
  leauth-proxy:
    networks:
      - default            # без явного упоминания сервис из неё выпадет
      - backend

networks:
  backend:
    external: true
```

После этого `upstream: http://<имя-контейнера>:<порт>` работает по
внутреннему DNS докера. Заодно это способ обойти авторизацию,
навешенную на публичный порт бэкенда: прокси ходит прямо в контейнер, а
пускать или нет — решает блок `oauth`.

## Авторизация через GitLab

Эндпоинт с блоком `oauth` пускает только тех, кто вошёл в GitLab.
Пустой блок `oauth: {}` пускает любого пользователя, `oauth.groups` —
только членов перечисленных групп, достаточно одной.

### Приложение в GitLab

Одно приложение на всю установку: **Admin → Applications** (или в профиле
пользователя, если ставите от своего имени).

- Scopes: `openid`, `profile`, `email`
- Redirect URI: по одной строке на каждый закрытый домен, вида
  `https://docs.example.com:9443/oauth2/callback`

Адрес redirect URI обязан совпадать побайтно с тем, что использует прокси.
Агент печатает итоговое значение в лог при старте:

    запускается oauth2-proxy домен=docs.example.com порт=4180
    redirect_uri=https://docs.example.com:9443/oauth2/callback группы=[platform/backend]

Порт входит в адрес. Если снаружи домен доступен на другом порту — через
балансировщик или проброс — задайте `external_url` у эндпоинта, иначе
GitLab отклонит вход.

Каждый новый закрытый домен требует новой строки здесь. Если доменов
много или они добавляются регулярно, это лишнее хождение убирается —
см. «Общий вход» ниже.

### Общий вход

По умолчанию у каждого закрытого домена свой процесс `oauth2-proxy` и
свой redirect URI в GitLab. Это просто и надёжно, но добавление домена
требует правки приложения GitLab — единственное ручное действие в системе
помимо CNAME.

`auth_domain` включает другой режим: вход для всех закрытых доменов
происходит на одном домене, процесс становится один, а в GitLab остаётся
**одна** строка redirect URI навсегда.

```yaml
oauth:
  issuer: https://gitlab.example.com
  client_id: ${GITLAB_CLIENT_ID}
  client_secret: ${GITLAB_CLIENT_SECRET}
  cookie_secret: ${OAUTH_COOKIE_SECRET}
  auth_domain: auth.example.com     # ← включает общий вход

endpoints:
  # Домен входа. Обычный эндпоинт: свой сертификат, свой CNAME.
  # Закрывать его не обязательно — на нём живут только служебные адреса.
  - domain: auth.example.com
    listen: 8443
    upstream: http://заглушка:80

  - domain: docs.example.com
    listen: 8443
    upstream: http://docs:8080
    oauth:
      groups: [platform/backend]

  # Новый закрытый домен — и всё, в GitLab возвращаться не нужно.
  - domain: wiki.example.com
    listen: 8443
    upstream: http://wiki:8080
    oauth:
      groups: [platform/sre]
```

В GitLab при этом одна строка:

    https://auth.example.com:8443/oauth2/callback

Разграничение по группам сохраняется в полном объёме: группы задаются
у каждого эндпоинта, как и раньше, и проверяются на каждом запросе самим
oauth2-proxy — точным совпадением, а не по подстроке. Человеку без нужной
группы приходит 403, а не повторный вход по кругу.

Как это работает: сессионная cookie ставится на общий родительский домен
(`example.com` в примере), поэтому вход, сделанный на `auth.example.com`,
виден и `docs.example.com`, и `wiki.example.com`. Вернуться после входа
можно только на объявленные в конфиге адреса.

Что нужно учитывать:

- **Все закрытые домены должны лежать под общим родительским доменом.**
  Cookie шире него не ставится. `docs.example.com` и `wiki.example.com` —
  годятся, `docs.example.com` и `docs.other-company.net` — нет; агент
  такой конфиг не примет и скажет об этом на старте.
- **Домен входа — обычный эндпоинт.** Ему нужен свой CNAME и сертификат;
  при `wildcard_zones` — не нужен и CNAME. `upstream` у него можно
  направить куда угодно: снаружи запрашиваются только пути `/oauth2/`.
- **Сессия общая на все закрытые домены зоны.** Это обычное поведение
  SSO, но стоит понимать: выход на одном домене — выход везде.
- **Процесс один на все домены.** Пока он перезапускается, вход не
  работает нигде; в режиме по умолчанию упавший процесс закрывал один
  домен. Супервизор перезапускает его так же, с нарастающей паузой.

Режим переключается в обе стороны: уберите `auth_domain` — вернётся
процесс на домен, и в GitLab снова понадобится строка на каждый.

### Переменные

Живут в `.env` рядом с `docker-compose.yml`, шаблон — `.env.example`.
Файл целиком уезжает в контейнер, поэтому любая своя переменная —
например пароль из `upstream_auth` — подставляется в `agent.yaml` как
`${ИМЯ}` без правки `docker-compose.yml`.

    LEAUTH_ENROLL_TOKEN=<общий токен приёма от администратора центра>
    GITLAB_CLIENT_ID=<из приложения GitLab>
    GITLAB_CLIENT_SECRET=<из приложения GitLab>
    OAUTH_COOKIE_SECRET=$(openssl rand -base64 32 | tr -- '+/' '-_')

`OAUTH_COOKIE_SECRET` шифрует сессионную cookie: он должен быть 16, 24 или
32 байта. Смена секрета разлогинивает всех.

`tr` здесь обязателен. oauth2-proxy декодирует секрет только как
base64url, поэтому вывод `openssl rand -base64 32` с символами `+` или
`/` доходит до него сырыми 44 символами, и процесс отказывается
стартовать: `cookie_secret must be 16, 24, or 32 bytes`. Символов этих в
выводе может и не оказаться — тогда тот же рецепт срабатывает через раз.

### Пути мимо авторизации

Если по тому же адресу живёт машинный интерфейс — API, `/healthz`,
вебхук, — его нужно вывести из-под входа через браузер:

```yaml
    oauth:
      groups: [platform/sre]
      skip_paths: [/api/, /healthz]
```

Перечисленные префиксы проксируются напрямую, всё остальное требует
GitLab. nginx выбирает наиболее длинный подходящий префикс, поэтому
`/api/` выигрывает у корневого `location /`.

Путь `/` в этом списке снял бы авторизацию целиком, поэтому агент его не
принимает — как и пути внутри `/oauth2/`, занятого самим oauth2-proxy.
Защита за `skip_paths` остаётся на совести бэкенда: центр, например,
проверяет там свои Bearer-токены.

### Что видит бэкенд

Прошедший авторизацию запрос приходит в upstream с заголовками
`X-Auth-Request-User`, `X-Auth-Request-Email` и `X-Auth-Request-Groups` —
приложение может разграничивать права само.

Плюс `X-Auth-Request-Preferred-Username`, если GitLab отдаёт claim
`preferred_username`.

Подделать их снаружи нельзя. Значения ставит сам прокси по результату
проверки сессии, а на всех путях, где авторизации нет, — на открытых
эндпоинтах и на `skip_paths` — весь префикс `X-Auth-Request-`
принудительно вычищается из запроса. До бэкенда эти заголовки доходят,
только если за ними стоит настоящий вход в GitLab.

Так же задаются заголовки о самом запросе: `Host`, `X-Real-IP`,
`X-Forwarded-For`, `-Proto`, `-Host` и `-Port`. Остальные признаки
«настоящего» адреса — `X-Forwarded-Prefix`, `-Uri`, `-Ssl`,
`X-Original-URL`, `X-Rewrite-URL` и подобные — вычищаются: по ним
приложения строят абсолютные ссылки, а некоторые фреймворки подменяют
путь запроса, и тогда адрес, пропущенный мимо авторизации через
`skip_paths`, обработался бы как совсем другой.

Единственное исключение — `X-Forwarded-For`: прокси дописывает реальный
адрес к присланному, как это принято, чтобы работала цепочка через
балансировщик. Клиентская часть цепочки при этом остаётся клиентской,
поэтому адрес брать нужно с конца списка, а не с начала.

Обратная сторона: на `skip_paths` бэкенд не узнает о клиенте ничего.
Пришедший туда запрос анонимен по определению, и проверять его — работа
самого бэкенда.

### Если авторизация не поднялась

oauth2-proxy при старте запрашивает у GitLab OIDC-конфигурацию и
завершается, если тот недоступен. Агент перезапускает его с нарастающей
паузой — от секунды до минуты. Пока процесс не поднялся, закрытые
эндпоинты отвечают ошибкой: отказ авторизации не открывает доступ.
Открытые эндпоинты продолжают работать.
