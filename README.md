# leauth

Закрывает внутренние HTTP-эндпоинты валидным TLS от Let's Encrypt и, по
желанию, авторизацией через GitLab. Сертификаты выпускаются и продлеваются
сами; от человека нужен один CNAME на домен — один раз за всё время.

Рассчитан на условия, в которых обычные ACME-клиенты не работают: порт 80
закрыт снаружи или занят, TLS поднимается на нестандартном порту, серверы
стоят за NAT, а домены живут в разных зонах, ключи от которых сервису
отдавать нельзя.

## Как это работает

```
                        ┌─ центральный хост (публичный IP) ─┐
   Let's Encrypt ──DNS──┤  acme-dns :53   leauth server     │
                        └──────────────┬────────────────────┘
                                       │ HTTPS, pull по токену
              ┌────────────────────────┼────────────────────────┐
      ┌───────┴────────┐      ┌────────┴───────┐      ┌─────────┴──────┐
      │ прокси-сервер  │      │ прокси-сервер  │      │ прокси-сервер  │
      │ nginx + agent  │      │ nginx + agent  │      │ nginx + agent  │
      └───────┬────────┘      └────────┬───────┘      └─────────┬──────┘
              └── бэкенды на localhost / в сети compose ────────┘
```

**Центр** выпускает сертификаты. `acme-dns` — авторитативный DNS для
служебной зоны: он хранит TXT-записи, по которым Let's Encrypt проверяет
владение доменом. `leauth server` ходит в Let's Encrypt, складывает
сертификаты в SQLite и отдаёт их по API.

**Прокси** стоит рядом с приложением. `leauth agent` раз в час объявляет
центру, какие сертификаты ему нужны и какие у него уже есть, забирает
обновлённые и перезагружает nginx. Всё это одним запросом; соединение
всегда исходящее, поэтому прокси может стоять за NAT. Пока хоть один
домен ждёт своего первого сертификата, прокси спрашивает центр раз в
минуту — чтобы выпущенный сертификат не лежал до конца часа.

Список эндпоинтов в конфиге прокси — желаемое состояние целиком:
добавленный домен заводится сам, удалённый снимается с обслуживания.

Ключевая идея: домен один раз делегирует проверку владения на ваш
`acme-dns` записью CNAME. Дальше продление идёт без единой правки DNS.

## Что нужно для запуска

- Один хост с публичным IP и свободным портом 53 (UDP и TCP) — под центр.
- Домен, которым вы управляете. Целиком отдавать не нужно: достаточно
  делегировать зону третьего уровня двумя записями.
- Docker с compose на центральном хосте и на каждом прокси-сервере.

## Разовая настройка: служебная зона

Две записи в зоне вашего домена, больше в ней ничего не меняется:

    ns-acme.example.com.  A   <публичный IP центрального хоста>
    acme.example.com.     NS  ns-acme.example.com.

Эта зона нужна постоянно: на выданные в ней имена ссылаются CNAME всех
ваших доменов.

## Запуск центра

Файла конфигурации у центра нет — всё в переменных окружения:

    cd deploy/central
    cp .env.example .env            # ACMEDNS_*, ACME_EMAIL, ADMIN_PASSWORD
    echo "LEAUTH_MASTER_KEY=$(openssl rand -hex 32)" >> .env
    echo "LEAUTH_ENROLL_TOKEN=$(openssl rand -hex 32)" >> .env
    docker compose up -d

Переменные центра (`deploy/central/.env`):

| Переменная | Значение |
|---|---|
| `ACMEDNS_ZONE` | делегированная зона, `acme.example.com` |
| `ACMEDNS_NS_HOST` | имя NS-сервера, `ns-acme.example.com` |
| `ACMEDNS_ADMIN` | почта админа зоны в форме SOA: `hostmaster.example.com` |
| `ACMEDNS_PUBLIC_IP` | публичный IP центрального хоста |
| `LEAUTH_MASTER_KEY` | 64 hex-символа, шифрует приватные ключи в БД |
| `LEAUTH_ENROLL_TOKEN` | общий токен, по которому прокси получают свои |
| `ACME_EMAIL` | почта для уведомлений Let's Encrypt |
| `ADMIN_PASSWORD` | пароль к странице статуса |

Проверка: `dig @<IP> acme.example.com SOA` должен ответить.

API центра слушает открытый HTTP и отдаёт по нему приватные ключи
сертификатов и токены прокси. В интернет его выставлять не нужно:
закройте порт файрволом либо поставьте перед центром прокси на том же
хосте — он выпишет центру сертификат и закроет API своим TLS. Порядок
переключения — в [deploy/central/README.md](deploy/central/README.md).

Подробности — [deploy/central/README.md](deploy/central/README.md).

## Запуск прокси

    cd deploy/proxy
    cp agent.yaml.example agent.yaml    # домены, порты, апстримы
    cp .env.example .env                # токен приёма с центра
    docker compose up -d

Прокси сам представляется центру и получает персональный токен, который
хранит в своём томе. На центре при этом ничего делать не нужно: токены
не выдают руками и не вписывают в конфиги.

Токен именует прокси, но не ограничивает его: любой принятый прокси может
запросить у центра любой домен установки и получить его приватный ключ.
Прокси в этой схеме равны по доверию — подробнее в
[deploy/central/README.md](deploy/central/README.md#что-даёт-персональный-токен).

Прокси поднимается сразу, на самоподписанном сертификате. В логе появится:

    нужен CNAME домен=docs.example.com запись=_acme-challenge.docs.example.com
    значение=<uuid>.acme.example.com

Пропишите этот CNAME в зоне домена. В пределах пяти минут центр выпустит
сертификат, агент его заберёт и перезагрузит nginx. Больше к DNS
возвращаться не нужно — ни при продлении, ни при переезде.

Каждый следующий домен: строка в `agent.yaml`, перезапуск контейнера,
один новый CNAME (у каждого домена свой, с собственным uuid).

Если поддомены живут в одной зоне, CNAME нужен один на всю зону:

```yaml
wildcard_zones:
  - example.com
```

Тогда на `example.com` и `*.example.com` выпускается один сертификат, а
все эндпоинты внутри зоны используют его. Новый поддомен после этого не
требует ни одной правки в DNS.

Подробности — [deploy/proxy/README.md](deploy/proxy/README.md).

## Авторизация через GitLab

Необязательна. Эндпоинт с блоком `oauth` пускает только тех, кто вошёл в
GitLab:

```yaml
oauth:
  issuer: https://gitlab.example.com
  client_id: ${GITLAB_CLIENT_ID}
  client_secret: ${GITLAB_CLIENT_SECRET}
  cookie_secret: ${OAUTH_COOKIE_SECRET}

endpoints:
  - domain: docs.example.com
    listen: 9443
    upstream: http://docs:8080
    oauth:
      groups: [platform/backend, platform/sre]   # пусто — любой из GitLab
```

В GitLab заводится одно приложение со scopes `openid`, `profile`, `email`
и списком redirect URI — по одному на закрытый домен, вида
`https://docs.example.com:9443/oauth2/callback`. Адрес должен совпадать
побайтно; агент печатает итоговое значение в лог при старте.

Чтобы не возвращаться в GitLab на каждый новый домен, есть общий вход:
одна строка `auth_domain` в конфиге — и redirect URI остаётся один на всю
установку, а разграничение по группам работает как прежде.

```yaml
oauth:
  auth_domain: auth.example.com
```

Условие — все закрытые домены под общим родительским доменом. Подробности
и оговорки — в [deploy/proxy/README.md](deploy/proxy/README.md#общий-вход).

Бэкенд получает запрос с заголовками `X-Auth-Request-User`, `-Email` и
`-Groups`. Снаружи они не подделываются: там, где авторизации нет, прокси
вычищает их из запроса.

## Образы

Готовые образы под `linux/amd64` лежат в GHCR:

    ghcr.io/wendor/leauth         # центр
    ghcr.io/wendor/leauth-proxy   # прокси: nginx + oauth2-proxy + агент

Compose-файлы в `deploy/` берут их сами. На боевом хосте версия
закрепляется в `.env` — `LEAUTH_TAG=v1.0.0`, — иначе поедет `latest`:

    docker compose pull && docker compose up -d

Секция `build` в тех же файлах никуда не делась: без `pull` compose
соберёт образ из исходников рядом, как и раньше.

### Публикация

Сборочная машина обычно arm64, серверы — amd64. Бинарь статический,
поэтому Go кросс-компилирует его без эмуляции — сборка идёт нативно:

    make tags      # какие имена получит следующая сборка
    make images    # собрать локально, под linux/amd64
    make login     # в GHCR, токеном gh
    make push      # собрать и отправить

Отдельный PAT для реестра не нужен: `make login` берёт токен у `gh`.
Права на пакеты в него нужно добавить один раз — `gh` их по умолчанию
не запрашивает:

    gh auth refresh -h github.com -s write:packages

Теги берутся из git: коммит с тегом `vX.Y.Z` даёт `vX.Y.Z` и `latest`,
любой другой — только `main-<sha>`. Публикация из грязного дерева
отклоняется: тег обязан соответствовать коммиту.

Публиковать в реестр, включая публичный, безопасно: в образах только
бинари и системные CA-сертификаты. Конфиги, ключи и база монтируются на
запуске.

## Обслуживание

Две операции, которые делаются на центре и не требуют его остановки:

    docker compose exec leauth leauth revoke srv-07          # отозвать прокси
    docker compose exec leauth leauth renew docs.example.com # перевыпустить

Отзыв гасит токен прокси и снимает с него домены. Перевыпуск нужен после
отзыва: ключи, которые прокси унёс с собой, иначе действуют до конца
срока сертификата. Порядок и оговорки —
в [deploy/central/README.md](deploy/central/README.md#отзыв-прокси).

## Что нельзя терять

- Тома `leauth-data` и `acme-dns-data` на центре — в них учётные данные
  acme-dns. При потере придётся переписать CNAME у всех доменов.
- `LEAUTH_MASTER_KEY` — без него приватные ключи в БД не расшифровать.

Оба пункта требуют бэкапа. Всё остальное восстанавливается перезапуском.

## Разработка

    make test          # модульные тесты
    make proxy         # конфиг nginx и заголовки на живом прокси
    make integration   # выпуск сертификата через pebble
    make e2e           # сквозной сценарий: центр, прокси, бэкенд

Боевой Let's Encrypt в тестах не используется; всё, что сложнее
модульных тестов, требует docker.

`make proxy` проверяет то, чего не видно сравнением строк: сгенерированный
конфиг скармливается настоящему nginx, запросы проходят через него
насквозь и сверяются с тем, что получил бэкенд, а аргументы oauth2-proxy
прогоняются через тот же образ, который попадает в боевой. Подделанные
заголовки, потерянный поток и переименованный флаг ловятся здесь.
